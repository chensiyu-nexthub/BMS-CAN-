# BMS项目简历写法与风险表述

> 目标：教你把这个 `BMS` 项目写进简历，同时避免把自己写进死角。  
> 核心原则：简历不是“写得越满越好”，而是“每一句都能扛追问”。  
> 适用主线：当前最稳妥的项目主线是 `STM32F103 + BQ76940 + 软件SOC + UART CLI + FreeRTOS双任务`。

---

## 1. 先把简历写法的底线说清楚

这类项目最容易出问题的地方，不是技术词不够多，而是叙述边界失控。

你现在手里的资料，明显由三层内容混合组成：

1. `当前代码已验证`：你可以结合源码、模块、流程直接讲的内容。
2. `根据资料理解的方案能力`：你可以讲“为什么这样设计”，但不能说成当前版本已经全部实现。
3. `暂未落地的扩展项`：你只能说“预留方向”“方案对比”“后续可扩展”，不能说“我做了”。

如果你把这三层混成一层，简历上的项目会显得很满，但面试官只要追问两轮，你就会暴露出“方案会背、实现没落地”的问题。

所以这份文档不是教你“怎么吹”，而是教你：

1. 哪些内容可以安全写。
2. 哪些内容必须降级表达。
3. 怎么在不虚构能力的前提下，把项目写得有价值。

---

## 2. 这三个边界必须死记住

### 2.1 当前代码已验证

当前较稳的已验证内容，应以你现有文档和代码主线为准：

1. 以 `STM32F103` 作为主控。
2. 以 `BQ76940` 作为电池采样与基础保护前端 `AFE`。
3. 通过 `I2C` 与 `BQ76940` 交互，获取单体电压、电流、温度等状态量。
4. 采用 `FreeRTOS` 双任务组织主流程。
5. 采用 `UART ASCII` 命令行方式进行调试与状态查看。
6. 当前版本具备采样、基础保护、基础均衡控制、软件 `SOC` 估算与串口交互闭环。

这些内容，是你简历里最应该优先写的“硬落地”内容。

### 2.2 根据资料理解的方案能力

这些内容可以写进“方案设计理解”“系统研究”“扩展预留”，但不能直接写成当前版本已全部落地：

1. 独立电量计与前端分工设计，例如 `BQ34Z100-G1` 与 `BQ76940` 的职责区分。
2. 更完整的多任务软件架构、状态机、故障管理、参数管理。
3. 更规范的均衡策略、故障恢复策略、保护迟滞与去抖设计。
4. 更完整的通信链路，例如 `CAN`、蓝牙、上位机扩展能力。
5. 高边驱动、预充控制、系统级保护执行链路设计。

这些内容的安全写法，不是“实现了”，而是：

1. `研究并梳理了`
2. `完成了方案设计与边界分析`
3. `对比了不同器件/架构的职责分工`
4. `形成了扩展设计思路`

### 2.3 暂未落地的扩展项

以下内容如果你当前没有代码、调试记录、验证结果支撑，就不要写成简历里的既成事实：

1. `BQ34Z100-G1` 已经接入并完成高精度 `SOC/SOH` 估算。
2. `bq76200` 已经完成高边驱动与预充管理闭环。
3. 已完成完整 `CAN + 蓝牙 + WiFi + Qt上位机` 通信体系。
4. 已实现完整故障日志、黑匣子、参数在线升级、远程配置。
5. 已完成完整量产级均衡控制、老化学习、容量学习、健康度建模。

这些内容不是不能讲，而是必须切换语态：

1. `属于方案层扩展方向`
2. `资料中已有参考设计`
3. `当前项目阶段主要完成了主线验证，扩展项暂未完全落地`

## 3. 简历写这类项目，正确目标是什么

你真正要达成的不是“让项目看起来像量产项目”，而是让面试官形成三个判断：

1. 你知道这个系统在解决什么问题。
2. 你知道当前版本到底实现到了什么程度。
3. 你对未落地部分也有清晰的架构理解和边界意识。

也就是说，最好的简历效果不是“看起来最豪华”，而是：

1. 项目主线清楚。
2. 技术关键词真实。
3. 你的职责和认知深度匹配。
4. 每一条都能接住追问。

这比堆满 `CAN`、`蓝牙`、`高精度电量计`、`复杂状态机` 更重要。

## 4. 项目标题怎么写

项目标题有两个任务：

1. 先把项目主线定死。
2. 不要在标题里就把自己吹穿。

### 4.1 不推荐的标题写法

以下写法风险很高：

1. `智能储能BMS量产系统开发`
2. `基于多协议通信的高精度BMS全栈开发`
3. `基于BQ34Z100和BQ76940的工业级电池管理平台`
4. `支持CAN/蓝牙/WiFi/云平台的完整BMS系统`

这些写法的问题在于：

1. 默认你已经做到了量产级。
2. 默认你已经把所有链路都落地了。
3. 默认你已经做了独立电量计和完整工业化能力。
4. 标题本身就会把追问难度拉满。

### 4.2 推荐的标题写法

以下写法更稳：

1. `基于STM32F103与BQ76940的多串锂电BMS验证项目`
2. `多串锂电池BMS采样、保护与软件SOC估算项目`
3. `基于BQ76940前端的BMS监测与控制验证系统`
4. `多串锂电BMS方案研究与验证实现项目`

这些写法的优点是：

1. 直接把主线器件写清楚。
2. 把“验证项目”而不是“量产平台”说清楚。
3. 既保留技术含量，又避免把自己锁死在过高承诺里。

## 5. 项目描述怎么写

项目描述是简历中最容易写空、也最容易写爆的部分。

一个合格的项目描述，至少要回答 4 件事：

1. 这项目做什么。
2. 为什么需要这个系统。
3. 当前实现主线是什么。
4. 你的工作重点在哪。

### 5.1 项目描述写法模板

可以按下面这个结构来写：

> 面向多串锂电池组的状态监测与安全管理需求，基于 `STM32F103` 与 `BQ76940` 构建 `BMS` 验证系统，完成电池单体电压、电流、温度采样、基础保护、基础均衡控制、软件 `SOC` 估算及 `UART` 调试链路验证，并对独立电量计、高边驱动、多通信链路等扩展方案进行对比研究。

这段话的优点是：

1. 前半句说系统目标。
2. 中间句说当前实现。
3. 结尾句说方案研究。
4. 把“已实现”和“研究过但未全部落地”分开了。

### 5.2 不推荐的项目描述

以下写法容易出事：

> 完成高精度电量计、CAN通信、蓝牙传输、上位机控制、故障日志、均衡系统、预充系统等完整BMS开发。

这段话的问题是：

1. 没有分清哪些是代码已做，哪些只是资料里有。
2. 一口气背了太多功能点，极易被逐条追杀。
3. 只要面试官问你 `CAN` 帧定义、`BQ34Z100` 参数学习、预充时序，你就会断。

---

## 6. 技术栈怎么写

技术栈不是把你见过的名词都列上去，而是只写你能解释其作用、在项目里真实出现过、并且能扛追问的内容。

### 6.1 推荐写法

当前更安全的技术栈写法：

1. `STM32F103`
2. `BQ76940`
3. `C`
4. `FreeRTOS`
5. `I2C`
6. `UART`
7. `软件SOC估算`
8. `电池采样 / 过压欠压过流保护 / 基础均衡控制`

如果要写成一行，可以这样写：

> 技术栈：`STM32F103`、`BQ76940`、`C`、`FreeRTOS`、`I2C`、`UART`、软件 `SOC` 估算、电池采样与基础保护

### 6.2 可以谨慎加上的内容

如果你想体现方案理解，可以单独放在“补充研究”或“方案扩展理解”语境下：

1. `BQ34Z100-G1` 职责对比
2. `bq76200` 高边驱动方案理解
3. `CAN` 上位机资料分析
4. 均衡策略与硬件约束分析

安全写法示例：

> 补充研究：对 `BQ34Z100-G1` 电量计方案、`bq76200` 高边驱动方案及 `CAN` 链路资料进行了对比分析。

### 6.3 不建议直接写进技术栈的内容

以下内容如果当前没有稳定落地证据，不建议直接混入主技术栈：

1. `BQ34Z100-G1`
2. `bq76200`
3. `CAN总线通信`
4. `蓝牙/WiFi`
5. `Qt上位机`
6. `SOH学习算法`
7. `ChemID / Ra Table / 阻抗跟踪`

原因很简单：一旦你把它们放进主技术栈，面试官会默认这些就是你真实做过的主战场。

## 7. 职责怎么写

职责部分一定要从“我负责了什么”来写，而不是从“整个系统所有模块都有什么”来写。

### 7.1 推荐职责写法原则

1. 优先写你看得懂、讲得顺、能落到模块的内容。
2. 尽量用“动词 + 对象 + 结果”的结构。
3. 不要把全项目所有能力都写成你的直接负责项。

### 7.2 可直接参考的职责写法

你可以从下面这些里选符合你实际掌握程度的条目：

1. 负责基于 `STM32F103` 与 `BQ76940` 的 `BMS` 主线方案梳理与代码理解，明确采样、保护、均衡与 `SOC` 模块的职责边界。
2. 结合 `BQ76940` 芯片资料与项目源码，梳理电池单体电压、电流、温度采样及基础保护流程。
3. 参与分析 `FreeRTOS` 双任务结构，理解并整理 `BMS_Task` 与 `UART_Task` 的主流程关系。
4. 结合源码阅读与资料对照，梳理软件 `SOC` 估算思路及其与采样数据、运行状态之间的关系。
5. 负责整理 `UART ASCII` 调试命令链路，明确状态查询、均衡控制、充放电控制等交互入口。
6. 对 `BQ34Z100-G1` 电量计方案、`bq76200` 高边驱动方案及历史 `CAN` 链路资料进行对比分析，区分当前实现与扩展方向。

### 7.3 职责写法的降风险技巧

如果你担心“负责”两个字太重，可以用以下表达替代：

1. `参与梳理`
2. `结合源码理解并整理`
3. `完成方案研究与对照分析`
4. `围绕主线模块完成阅读、验证与总结`

这些表达更适合你当前处于“深入理解并可讲清”但不一定全程亲手从零开发的状态。

## 8. 亮点怎么写

亮点不是“列功能”，而是“说出你比普通抄代码的人多做了什么理解或拆解”。

### 8.1 推荐亮点方向

你这个项目真正适合写的亮点，不是豪华功能，而是下面这些：

1. 把 `BQ76940` 的 `AFE` 定位讲清楚，而不是把它误写成电量计。
2. 把“当前代码实现”“方案能力”“扩展预留”三层边界分清。
3. 能从采样、保护、均衡、`SOC` 四条主线解释系统运行逻辑。
4. 能明确指出 `UART` 是当前调试主链路，而 `CAN` 等资料属于历史或扩展链路。
5. 能说明软件 `SOC` 的误差来源、边界条件和工程局限，而不是把 `SOC` 简化成“电压百分比”。

### 8.2 亮点写法示例

可以直接参考：

1. 梳理并建立了 `BMS` 项目中“采样前端、主控策略、软件 `SOC`、调试通信”四层职责划分，避免将理论方案与当前实现混淆。
2. 结合 `BQ76940` 芯片资料和源码主线，整理了采样、保护、均衡之间的执行关系及硬件约束。
3. 对软件 `SOC` 估算中初值估计、积分漂移、容量衰减、负载压降等误差来源进行了系统分析。
4. 对独立电量计、高边驱动、`CAN` 链路等扩展方案进行了资料研究，并与当前验证版主线做边界区分。

### 8.3 不推荐的亮点写法

以下亮点风险过高：

1. `独立完成高精度SOC/SOH算法开发`
2. `实现工业级CAN组网与远程监控平台`
3. `完成量产级预充、高边MOS驱动与黑匣子系统`
4. `实现完整电池健康度学习与寿命预测模型`

如果这些没有完整代码和验证结果支撑，就不要往自己身上背。

## 9. 哪些话不能写

下面这些话，当前阶段不建议直接写进简历，除非你真的能拿出代码、日志、参数、流程和验证结果来证明。

### 9.1 绝对高风险写法

1. `独立开发完整量产级BMS系统`
2. `完成BQ34Z100-G1高精度电量计开发`
3. `实现完整CAN/蓝牙/WiFi多协议通信`
4. `实现SOH学习、ChemID建模、Ra Table管理`
5. `完成预充、高边驱动、故障快照、远程升级全链路`
6. `负责整套硬件设计、嵌入式开发、上位机开发和算法开发`

这些话的问题不是“听起来厉害”，而是它们默认你掌握了太多深水区细节。

### 9.2 容易误伤自己的模糊写法

下面这些话表面不夸张，但也容易让人误解：

1. `负责BMS系统总体开发`
2. `完成电量计与保护系统设计`
3. `实现多通信协议交互`
4. `开发均衡控制系统`

这些表达太宽泛。面试官会默认你做的是“从方案到实现的全链路”，而不是你当前更接近的“基于现有方案和代码主线进行深入理解、梳理、验证与整理”。

## 10. 哪些话可以保守写

如果你担心简历写得太硬，最安全的做法不是写得很空，而是换成“保守但有信息量”的表达。

### 10.1 保守写法模板

1. `基于`
2. `围绕`
3. `参与`
4. `梳理`
5. `分析`
6. `完成主线验证`
7. `形成方案理解`
8. `区分当前实现与扩展方向`

### 10.2 可直接用的保守句式

1. 基于 `STM32F103 + BQ76940` 主线，完成多串锂电 `BMS` 采样、保护与软件 `SOC` 估算流程的理解与验证。
2. 围绕 `BQ76940` 前端采样与保护链路，梳理单体电压、电流、温度采集及均衡控制关系。
3. 结合源码与芯片资料，分析软件 `SOC` 估算流程及其误差来源。
4. 对独立电量计、高边驱动与 `CAN` 等扩展方案进行了资料对照与边界整理。

这些写法的好处是：

1. 不虚。
2. 不空。
3. 还能体现你的理解深度。

## 11. 三套简历版本

下面给出三套可直接参考的版本。你要根据你后续真实掌握程度来选，而不是默认选最猛的。

### 11.1 保守版

适用场景：

1. 你目前更强调“理解透”和“能扛追问”。
2. 你还不想在简历上背太多实现责任。
3. 你希望面试时先稳住基本盘。

#### 项目标题

`基于STM32F103与BQ76940的多串锂电BMS验证项目`

#### 项目描述

面向多串锂电池状态监测与安全管理需求，基于 `STM32F103` 与 `BQ76940` 搭建 `BMS` 验证项目，围绕单体电压、电流、温度采样、基础保护、软件 `SOC` 估算及 `UART` 调试链路开展方案学习、源码理解与主线验证。

#### 技术栈

`STM32F103`、`BQ76940`、`C`、`FreeRTOS`、`I2C`、`UART`、软件 `SOC` 估算

#### 职责写法

1. 结合源码与芯片资料，梳理 `BQ76940` 采样、保护、均衡控制的主线流程。
2. 分析 `FreeRTOS` 双任务结构及 `UART` 命令调试链路。
3. 结合项目代码理解软件 `SOC` 估算思路，并整理误差来源与边界条件。
4. 对独立电量计、高边驱动、`CAN` 等扩展方案进行资料对比与边界区分。

#### 亮点写法

1. 明确区分当前代码主线实现与扩展方案，避免将资料能力误当作现有功能。
2. 能从采样、保护、均衡、`SOC` 四条主线解释系统运行逻辑。

#### 风险评价

这是最稳的一版，牺牲了一些“猛感”，但极大降低了被追问击穿的风险。

### 11.2 正常版

适用场景：

1. 你已经能顺着 `main.c -> bq76940.c -> bms_soc.c -> usart.c` 把主线讲明白。
2. 你希望简历看起来既真实又有一定项目深度。

#### 项目标题

`基于BQ76940前端的多串锂电BMS采样、保护与软件SOC项目`

#### 项目描述

基于 `STM32F103 + BQ76940` 搭建多串锂电 `BMS` 验证系统，完成单体电压、电流、温度采样、基础保护、基础均衡控制、软件 `SOC` 估算及 `UART ASCII` 调试链路主线验证，并对独立电量计、高边驱动及 `CAN` 等扩展方案进行了对比研究。

#### 技术栈

`STM32F103`、`BQ76940`、`C`、`FreeRTOS`、`I2C`、`UART ASCII`、软件 `SOC` 估算、电池采样与基础保护

#### 职责写法

1. 梳理 `STM32F103` 与 `BQ76940` 的分工关系，明确 `AFE` 前端、主控策略与调试通信之间的模块边界。
2. 结合源码阅读，分析电池采样、保护判断、均衡控制与串口交互的主流程。

#### 亮点写法

#### 风险评价

这是最推荐的一版。信息量足够，边界也相对安全。

### 11.3 进取版

适用场景：

1. 你后续确实能把源码主线、模块职责、关键命令、主要寄存器交互都讲得比较稳。

`基于STM32F103、BQ76940与FreeRTOS的多串锂电BMS主线验证与方案设计项目`

`STM32F103`、`BQ76940`、`C`、`FreeRTOS`、`I2C`、`UART ASCII`、软件 `SOC` 估算、均衡控制、电池保护策略分析

## 12. 三套版本怎么选

选版本不是看你想不想显得厉害，而是看你能不能抗住对应追问。

### 12.1 什么时候选保守版

1. 你还在消化主线。
2. 你最怕面试官深挖实现。
3. 你优先想要“稳”。

### 12.2 什么时候选正常版

1. 你已经能讲清项目主链路。
2. 你已经知道 `BQ76940`、软件 `SOC`、`UART` 主线各自负责什么。
3. 你想让简历有强度，但不想赌过头。

### 12.3 什么时候选进取版

1. 你已经能脱稿讲源码主线。
2. 你能回答当前实现和扩展方案的边界。
3. 你愿意为更强表达承担更高追问压力。

我的建议很直接：

如果你现在还在补资料和整理主线，优先用 `正常版`。  
`保守版` 适合特别求稳。  
`进取版` 不要提前用。

## 15. 简历写法风险清单

下面这份清单，建议你每次改简历前都过一遍。

### 15.1 标题风险

1. 有没有把“验证项目”写成“量产平台”。
2. 有没有在标题里就塞进 `CAN`、蓝牙、独立电量计、高边驱动等高风险关键词。
3. 标题是否已经超出当前代码主线。

### 15.2 项目描述风险

1. 有没有把“方案理解”写成“全部已实现”。
2. 有没有一次性堆太多功能点却不分层。
3. 有没有把历史资料链路写成当前主线链路。

### 15.3 技术栈风险

1. 有没有把 `BQ34Z100-G1`、`bq76200`、`CAN`、蓝牙等未稳落地内容直接塞进主技术栈。
2. 有没有写你其实说不清用途的技术名词。
3. 技术栈是否和项目描述一致。

### 15.4 职责风险

1. 有没有把“理解、梳理、对照分析”夸写成“独立开发全部模块”。
2. 有没有把全项目所有工作都背成自己一个人的责任。
3. 每一条职责是否都能落到模块、流程或资料依据。

### 15.5 亮点风险

1. 亮点是在说“理解深度”，还是在乱堆“功能数量”。
2. 亮点是否需要你回答大量当前没有把握的实现细节。
3. 亮点是否在无形中把方案项说成了现实现状。

### 15.6 面试联动风险

1. 简历上的每一个名词，你能不能说出“它在项目里负责什么”。
2. 简历上的每一句话，你能不能回答“为什么这么设计”。
3. 简历上的每一个模块，你能不能区分“已实现 / 方案理解 / 扩展预留”。

## 16. 最后的建议

你当前最该防的，不是“简历不够亮”，而是“为了变亮，把自己写虚了”。

真正有效的简历策略不是把项目包装成量产大而全，而是：

1. 把当前主线写实。
2. 把方案理解写深。
3. 把扩展方向写成边界清晰的研究项。

这样你后面不但能把项目写进简历，还能把项目讲进面试。
