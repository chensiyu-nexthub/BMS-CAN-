# BMS项目答辩讲稿版

## 1. 开场定位

各位老师好，下面我汇报的项目，是一个基于 `STM32F103` 和 `BQ76940` 的多串锂电池 `BMS` 验证版项目。  
我这次汇报不会把它讲成一个已经完全量产化的成品系统，而是重点讲清楚三件事：

1. 这个项目为什么要做。
2. 当前这套系统的硬件和软件主线是什么。
3. 哪些内容已经在当前代码里落地，哪些内容仍然属于方案研究和后续扩展。

我这样讲的目的是保证项目表达和当前代码、现有资料保持一致，避免把方案内容和实现内容混在一起。

---

## 2. 项目目标

如果用一句话概括，这个项目的目标就是：  
围绕多串锂电池组，完成采样监测、基础保护、均衡控制和基础 `SOC` 估算，先把一条能运行、能解释、能继续扩展的 `BMS` 主线搭起来。

做这个项目的原因也比较直接。多串锂电池在储能、机器人、小型电动车这些场景里很常见，但串数一上来，问题就不是“电池能不能供电”这么简单了，而是会同时遇到下面这些风险：

1. 单体不一致会越来越明显。
2. 容易出现过充、过放、过流、短路、过温等安全问题。
3. 只看总压，不足以真实反映整包剩余可用能量。
4. 如果没有均衡和状态管理，最弱单体会最先限制整包性能。

所以这个项目不是单纯做一个“电池能亮起来”的实验，而是想把安全监测、状态估算和系统分工建立起来。

---

## 3. 硬件方案

先说硬件分工。当前这套系统里，我把硬件主线理解成：

`电池组 -> BQ76940 -> STM32F103 -> 串口调试/上位机`

这里最核心的器件是 `BQ76940`。  
但我会先明确一个边界：`BQ76940` 的定位是 `AFE`，也就是电池监控前端，不是独立电量计，也不是完整 `BMS` 主控。

它在系统里主要负责几类事情：

1. 采集单体电压。
2. 提供电流检测基础。
3. 采集温度信息。
4. 提供过压、欠压、过流、短路等基础硬件保护能力。
5. 提供 `CHG`、`DSG`、`ALERT` 和均衡控制资源。

也就是说，`BQ76940` 更像是离电池最近的一层，它负责把电池侧最关键的原始量和底层安全能力先标准化。

主控这边选的是 `STM32F103`。  
我对它的理解不是“它自己去做所有模拟采样”，而是它站在系统控制层，负责：

1. 初始化系统和外设。
2. 通过 `I2C` 读取 `BQ76940` 的寄存器数据。
3. 做状态更新和保护判断。
4. 做软件 `SOC` 估算。
5. 处理串口调试和状态交互。

从硬件思路上，这样分工的好处是比较清楚：  
电池前端的高压多串采样和基础保护交给 `BQ76940`，系统组织、状态逻辑和对外交互交给 `STM32`。

这里我还会主动说明一个边界：  
资料里确实出现过 `BQ34Z100-G1` 和 `bq76200`。

但在当前这份项目代码主线里：

1. `BQ34Z100-G1` 没有真正落成独立电量计主线。
2. `bq76200` 也没有形成当前代码里的独立高边驱动实现。

所以它们在这次汇报里，只能作为方案对比或扩展方向来理解，不能说成当前已经落地。

---

## 4. 软件方案

软件这边，我会先讲总思路，再讲当前代码主线。

总思路其实可以概括成一句话：  
先采样，再判断，再执行，最后对外输出结果。

如果拆开看，软件主要在做下面几层事情：

1. 采样层：读取电压、电流、温度和状态位。
2. 状态判断层：判断当前处于充电、放电、静置还是故障状态。
3. 保护执行层：根据阈值和状态控制充放电路径。
4. 算法层：做 `SOC` 估算和状态更新。
5. 通信交互层：把结果通过串口输出，并接收调试命令。

当前代码不是那种非常复杂的大型产品级任务架构，而是一个比较清晰的验证版主线。  
它的主组织方式是 `FreeRTOS` 双任务，这一点很重要，因为它说明当前实现重点是先把主链路跑通，而不是先把架构做得特别庞大。

我现在对它的理解是：

1. `BMS_Task` 负责采样、保护、均衡控制和 `SOC` 更新这条电池状态主线。
2. `UART_Task` 负责串口命令接收、命令解析和状态交互。

这样拆分的好处是：  
安全相关的主链路和人机调试交互链路被分开了，逻辑上更容易讲清楚，也更方便后续扩展。

---

## 5. SOC 思路

`SOC` 是这个项目里最容易讲浅、也最容易被追问的部分，所以我会单独拿出来讲。

我对 `SOC` 的理解不是“看一下电压，然后算一个百分比”，而是：  
`SOC` 本质上是剩余可用容量状态的估算值，不是一个能被直接测出来的物理量。

为什么不能只看电压？主要有几个原因：

1. 电池带载时的端电压会受到内阻压降影响。
2. 线路本身也会带来压降。
3. 温度变化会影响电池电压和可用容量。
4. 电压和 `SOC` 关系本身不是线性的，尤其低电量区更明显。
5. 电池老化后，同样的电压不再代表同样的剩余容量。

所以当前项目里更合理的 `SOC` 理解，是一条“初值估计 + 在线跟踪 + 条件修正”的路线。

可以把它拆成三步：

1. 上电或者静置后，用开路电压关系给 `SOC` 一个初始值。
2. 运行过程中，主要靠电流积分持续跟踪容量变化。
3. 在满充、空电或者静置条件下，再对积分结果做修正。

也就是说：

1. 开路电压法负责定初值和纠偏。
2. 安时积分法负责运行中的连续跟踪。
3. 边界校准负责抑制长期漂移。

这里我也会主动承认当前实现的边界：  
当前代码走的是软件 `SOC` 主线，不是独立电量计直接给结果。

所以这套 `SOC` 方案的定位，更准确地说是：  
已经形成了基础可运行、可讲清楚的 `SOC` 闭环，但还不能直接等同于成熟商用 `gauge` 的精度体系。

## 6. 保护与均衡

### 6.1 保护

我对保护的理解是：  
保护不是附加功能，而是 `BMS` 的第一优先级。

因为 `SOC` 算错，通常先影响的是续航判断和使用体验；  
但保护失效，影响的是电池安全本身。

所以在系统主线上，保护一定优先于：

1. 均衡。
2. 通信。
3. 界面显示。
4. 算法精度优化。

我会把保护链路讲成下面这个顺序：

1. 周期读取单体电压、电流、温度和状态位。
2. 判断是否触发过压、欠压、过流、短路、过温等异常。
3. 如果异常成立，优先执行对应保护动作。
4. 再更新故障状态并通过调试接口输出。

这个顺序很重要，因为它体现的是：  
先保护，再上报，而不是先通信再决定要不要保护。

### 6.2 均衡

均衡这部分我也不会把它讲成“有压差就开”。  
更准确地说，均衡的目标是改善单体一致性，减少最弱单体对整包容量和安全边界的提前限制。

为什么要做均衡？因为多串电池长期使用以后，单体差异会越来越明显，原因可能包括：

1. 初始容量差异。
2. 内阻差异。
3. 温度分布不同。
4. 老化程度不同。
5. 充放电历史不同。

所以均衡的本质不是简单泄放，而是在处理一致性问题。

均衡的触发也不是单条件，而是通常要同时看：

1. 当前工作状态是否适合均衡。
2. 单体压差是否达到阈值。
3. 最高单体电压是否进入允许区间。
4. 当前温度是否允许。
5. 是否存在保护故障。

另外，`BQ76940` 这类芯片还有明确的硬件边界：  
同一组内相邻单体不能同时均衡。

所以我在汇报里会把它总结成一句话：  
均衡是建立在采样结果、状态判断和硬件约束共同成立前提下的控制动作，而不是一个常开功能。

## 7. 当前代码主线

接下来我会把当前代码能证明的主线讲清楚。

我现在对代码主线的归纳是：

`main.c -> bq76940.c -> bms_soc.c -> usart.c -> sw_i2c.c`

如果按系统启动过程来讲，大致是这样：

1. `main.c` 完成系统入口和基础外设初始化。
2. 初始化串口、DMA、GPIO、看门狗以及软件 `I2C`。
3. 初始化 `BQ76940` 和 `SOC` 模块。
4. 创建 `FreeRTOS` 任务。
5. `BMS_Task` 周期读取采样数据，完成状态更新、保护判断和 `SOC` 更新。
6. `UART_Task` 负责命令解析、状态查询以及调试控制。

如果按模块职责来讲，我会这样说：

1. `main.c` 负责把系统启动起来，并创建任务主框架。
2. `bq76940.c` 负责和前端芯片交互，完成寄存器读写、采样值获取和底层控制。
3. `bms_soc.c` 负责 `SOC/SOH` 相关的软件计算逻辑。
4. `usart.c` 负责串口接收、发送和命令处理。
5. `sw_i2c.c` 负责模拟 `I2C` 通信支撑。

当前代码真正落地的通信主线，我会明确讲成：  
`UART ASCII` 命令行调试链路。

因为现有资料里虽然还出现了 `CAN`、蓝牙和历史协议，但就当前主线代码能证明的部分来看，主入口仍然是串口命令调试，而不是完整 `CAN` 工业主链路。

## 8. 方案与实现边界

这一部分我会在答辩里主动说出来，因为这是整个项目最容易失真的地方。

我会把项目内容严格分成三层：

### 8.1 当前代码已实现

这部分是我可以结合代码直接讲的：

1. `STM32F103` 作为主控。
2. `BQ76940` 作为采样与保护前端。
3. 软件 `SOC` 估算主线。
4. `FreeRTOS` 双任务组织。
5. `UART ASCII` 命令调试与状态交互。
6. 基础采样、保护、均衡控制入口和串口闭环。

### 8.2 理论方案理解

这部分是我基于资料建立起来的系统认知：

1. `BQ76940` 为什么是 `AFE` 而不是电量计。
2. `SOC` 为什么不能简单按电压估百分比。
3. 均衡为什么不能简单理解成“压差大就开”。
4. 为什么高串系统里采样滤波、供电、布局和参考地都很关键。

### 8.3 扩展预留内容

这部分我不会说成“当前已经实现”，而只会说成方案或后续方向：

1. `BQ34Z100-G1` 独立电量计方案。
2. `bq76200` 高边驱动与预充方案。
3. 更完整的 `CAN` 或多链路通信架构。
4. 更复杂的故障日志、参数管理和产品级状态机。

我主动区分这三层，不是为了把项目讲小，而是为了让汇报更可信。  
因为这个项目最大的风险，不是内容不够，而是很容易把资料里提到过的能力，顺手讲成当前代码已经全部做完。

---

## 9. 结尾总结

最后我会把整个项目收成一句比较稳的话：

这个项目本质上是在做一套基于 `STM32F103` 和 `BQ76940` 的多串锂电池 `BMS` 验证系统。  
其中 `BQ76940` 负责采样、基础保护和均衡控制资源提供，`STM32F103` 负责系统组织、状态更新、软件 `SOC` 估算和串口交互。当前代码已经把采样、保护、基础 `SOC` 和调试主链路跑通了；而资料里出现的独立电量计、高边驱动、`CAN` 等内容，我会明确看作方案研究和后续扩展方向，不会混成当前实现。

如果从我自己的收获来总结，这个项目真正让我建立起来的，不是对某几个芯片名字的记忆，而是下面这几条主线：

1. `BMS` 首先是一个安全系统，保护优先级最高。
2. `SOC` 是估算问题，不是直接测量问题。
3. `BQ76940` 是前端采样保护芯片，不是独立电量计。
4. 均衡要服从状态、温度和硬件约束，不能想当然。
5. 项目表达必须严格区分“当前实现”和“方案扩展”。

我的汇报部分就是这些。

## 10. 老师或面试官打断后，如何回到主线

答辩过程中很容易被打断。  
真正的问题通常不是“答不上来”，而是被打断以后把整条主线讲乱了。

所以我建议你固定用下面这几种回主线的话术。

### 10.1 如果对方追问某个芯片细节

可以先回答追问，再这样拉回：

“这个点本质上还是服务于我刚才说的主线，也就是 `BQ76940` 负责前端采样和基础保护，`STM32` 负责上层状态和策略。我接着往下讲当前代码主线。”  

### 10.2 如果对方把话题带到 `BQ34Z100-G1`、`bq76200` 或 `CAN`

可以这样回：

“这部分在资料里属于方案扩展或历史链路，我这里先把当前代码已经落地的主线讲完，也就是 `STM32F103 + BQ76940 + 软件SOC + UART`，后面如果老师需要，我再单独展开扩展方案。”  

### 10.3 如果对方一直追着问 `SOC`

可以这样收束：

“`SOC` 这部分我先给一个结论，就是它本质上是估算问题，不是直接测量问题。当前实现是软件积分加条件修正。这个结论讲清楚以后，我再回到整体系统主线。”  

### 10.4 如果对方追问保护和均衡谁优先

可以这样回：

“这个问题我这里先给明确结论，保护优先于均衡和通信。因为安全是底线。基于这个优先级，再去理解均衡和串口交互就不会乱。”  

### 10.5 如果自己回答到一半有点散

可以直接用一句话重置结构：

“我重新收一下主线：这个项目先是 `BQ76940` 采样，接着 `STM32` 做判断和 `SOC` 更新，然后执行保护或均衡，最后通过串口输出状态。”  

### 10.6 最稳的统一回主线句式

如果你只记一句，我建议记这个：

“我先回到当前这份代码真正落地的主线，也就是 `采样 -> 判断 -> 执行 -> 输出`。在这条主线上，`BQ76940` 负责前端，`STM32` 负责上层逻辑，保护优先于均衡和通信。”  

这句话几乎可以把大部分被打断后的场面重新拉回来。
